## STAR 面试讲法

### S — 场景

企业制度、流程和产品资料通常散落在多份文档中。普通关键词搜索无法直接回答问题，而只使用大模型又容易产生无来源结论；云端模型或网络不可用时，应用也可能整体失效。

### T — 目标

实现一个本地可运行的知识库问答原型：回答必须基于上传文档、可以定位原文，在主模型异常时仍保持基本可用，同时提供面向非技术用户的管理界面。

### A — 行动

1. 将文档按知识库隔离，解析后清洗并重叠分块，向量与文档/页码元数据一起写入 Qdrant。
2. 并行执行 Dense 和 BM25 检索，以加权 RRF 合并候选，避免纯向量检索遗漏编号、专有名词和精确条款。
3. 在生成前设置证据门控和上下文上限，在 Prompt 中把文档标记为不可信证据，并在生成后校验引用编号。
4. 抽象 OpenAI-compatible 模型客户端，按 DeepSeek、Ollama、抽取式答案顺序降级，并把实际生成来源返回给界面。
5. 用 FastAPI 暴露业务 API，以 React 实现知识库、上传、问答、引用和会话管理，并用自动化测试覆盖关键路径。

### R — 结果

- 打通从文档上传到带页码引用回答的完整 RAG 链路。
- 在云端 LLM 或本地模型失败时仍能返回可核验的原文依据，避免服务完全不可用。
- 当前后端测试基线为 59 项全部通过，前端通过 TypeScript 类型检查与生产构建。

## 一分钟项目介绍

> 这个项目解决的是企业文档“能查到但不好问、模型能回答但不可信”的问题。系统把 PDF、TXT 或 Markdown 解析分块后写入 Qdrant，提问时同时做向量检索和 BM25 关键词检索，再通过加权 RRF 合并结果。进入模型前有证据门控和上下文预算，模型回答后还会校验 `[S1]` 形式的引用，因此前端可以展示文档名、页码和原文片段。生成层使用 OpenAI-compatible 接口，当前配置是 DeepSeek 主模型，失败后自动切换本机 Ollama；两者都不可用时返回抽取式答案。前后端分别采用 FastAPI 和 React，并实现了知识库、上传、对话历史、会话删除和 Agent 执行轨迹。

## 常见追问与回答要点

### 为什么不用纯向量检索？

企业文档中常见制度编号、金额、日期、产品型号和缩写。Dense 检索擅长语义相似，BM25 对精确词项更敏感；两者用 RRF 融合可以减少单一路径的偏差，也避免直接比较不同量纲的原始分数。

### 为什么用 RRF，而不是直接把分数相加？

向量相似度和 BM25 分数的范围、分布不同，直接线性相加依赖额外归一化。RRF 主要利用排序名次，对检索器分数尺度不敏感，适合作为简单稳定的融合基线。项目再用 `0.65 / 0.35` 表达语义召回优先级。

### 如何减少幻觉？

系统不是只依赖一句 Prompt，而是组合使用证据门控、最大上下文、明确的证据边界、文档指令不可信规则和生成后引用校验。若没有足够证据就拒答；若引用缺失或越界则改用抽取式答案。

### DeepSeek 切换 Ollama 的触发条件是什么？

主模型连接失败、超时、HTTP 错误、返回非预期 JSON 或空回答时进入二级模型。Ollama 同样失败后，系统从前几条高相关证据中选择与问题词项最匹配的句子，返回带来源编号的摘录。

### 本地 hashing embedding 有什么局限？

它无需下载模型，适合让项目开箱运行和验证工程链路，但语义泛化能力不等同于训练过的向量模型。生产环境应接入 BGE 等语义 embedding，建立标注问题集，使用 Recall@K、MRR 或 nDCG 评估，并在换模型时重建 collection。

### 为什么元数据使用 SQLite、向量使用 Qdrant？

两类数据的访问模式不同。知识库、文档状态和会话适合关系模型与事务；分块向量及检索 payload 适合向量数据库。单机原型用 SQLite 降低部署成本，生产可替换 PostgreSQL，同时保留 Qdrant 接口。

### 目前离生产还有哪些差距？

还需要 OIDC/SSO、租户和文档 ACL、审计与限流、异步摄取、对象存储、OCR、密钥托管、可观测性、备份恢复，以及基于真实问题集的检索/回答评测。能明确这些边界，比把原型描述成“生产级系统”更可信。
